# Customization

The core stays generic. Each repo, profile, and task adds specificity through set files. This file
defines where specificity goes and which layer wins.

## Layers

| Order | Layer | Where | Example content |
| --- | --- | --- | --- |
| 1 | Framework core | `framework/` in this repo | Principles, gates, profiles |
| 2 | Adapter and model profile | `framework/adapters/<name>.md`, its templates, and `framework/adapters/<name>/models/` | File paths for one harness. Idioms and role models for one model family. |
| 3 | Repo config | `.cornerstone/config.yaml` in the target repo | Commands, paths, limits, owners |
| 4 | Profile override | `.cornerstone/profiles/<profile>.yaml` in the target repo | Extra checks, a different size limit |
| 5 | Task | The ticket fields | Acceptance criteria, non-goals, a mode, a waiver |

A later layer wins over an earlier layer, with these limits:

1. A later layer MAY add a gate, a check, or a protected path.
2. A later layer MAY tighten a limit.
3. A later layer MUST record a waiver to remove a gate, remove a check, or loosen a limit. A waiver
   has a reason, an owner, and an end date.
4. No layer can remove G3 or G5 (see [gates.md](gates.md)).
5. Any layer MAY change the [mode](modes.md) or single stage drivers. A mode change never changes
   the gates.

## Repo config (`.cornerstone/config.yaml`)

```yaml
framework_version: 0.5.0           # tag of brawblan/ai-workflow. G3 installs stone from it.
harness: <harness-adapter-name>    # a file name in framework/adapters/
model_profile: <model-family>      # a file in framework/adapters/<harness>/models/
spec_tool: plain                   # plain, or a spec-tool adapter name
profiles: [single-ticket, bug-triage, debugging]
branches:
  integration: dev
  main: main
commands:                          # exactly as a person types them
  install: <command>
  lint: <command>
  typecheck: <command>
  test_unit: <command>
  test_acceptance: <command>
  all_checks: <command>
paths:
  source: [src/]
  tests: [tests/]                  # protected for the implementer
  checks: [.github/workflows/, .cornerstone/checks/]
  plans: docs/plans/
  specs: docs/specs/                # generated by stone spec apply
  reports: docs/reports/            # findings reports of the investigator
limits:
  pr_changed_lines: 600
  function_lines: 60
  cyclomatic: 10
  mutation_score_changed_code: 0.6
owners:
  default: <github-username>
  solo: false                      # true if one human fills all human roles (see modes.md)
modes_allowed: [agent-centric, hybrid, human-centric]   # the generator renders files for these
modes:                             # optional: change the default preset of a profile
  single-ticket: agent-centric
writing:
  standard: ste                    # see writing.md
  dictionary: docs/style/ste.md    # optional project dictionary
  max_words_procedure: 20
  max_words_description: 25
waivers: []
```

The generator fills the facts that it can find. It asks a human for the rest. It writes
`TODO(<owner>)` for an unknown value. It does not guess.

## Profile override (`.cornerstone/profiles/<profile>.yaml`)

```yaml
extends: single-ticket
mode: hybrid
drivers:                           # optional: change single stages of the preset
  plan: pair
checks_add: [K8]
limits:
  pr_changed_lines: 250
waivers:
  - gate: G4
    reason: <reason>
    owner: <github-username>
    until: 2027-01-31
```

## Task layer (ticket fields)

A ticket MAY set the mode for one item, for example with a field or a label `mode:human-centric`. If
the ticket sets no mode, the profile override or the repo config decides. If neither sets one, the
profile default applies.

## Hand-written components

A repo can add its own rules, skills, roles, or hooks. Put them in `.cornerstone/local/`. Add each one
to the manifest with `source: repo`. The lifecycle rules apply to them too.
